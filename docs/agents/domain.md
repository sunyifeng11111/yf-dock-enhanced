# Domain Docs

This project has a single domain context: root `GLOSSARY.md` and `docs/adr/`.

Before exploring domain behavior, read the existing glossary and relevant ADRs. Proceed when these files are absent; create them only when a term is settled or a decision warrants a record.

Use the glossary's canonical names in specs, tickets, code, and explanations. Keep the glossary limited to domain definitions; put behavior in specs and implementation trade-offs in ADRs.

If a proposed change contradicts an ADR, state the conflict and reason for reconsidering it before changing the decision.
